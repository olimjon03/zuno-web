# Saved bookmarks and listing likes

Apply `supabase/migrations/202611030014_listing_likes.sql` once in Supabase SQL Editor after migration 013. The migration has not been applied to the hosted database by this change. Until it is applied, older engagement rows still show views and messagers, while the unavailable like counter is omitted. Sample cards do not invent public likes.

Saved now uses the rounded bookmark icon consistently across the header, mobile navigation, account shortcuts, message workspace, listing cards and listing detail. Existing favorites and the Saved page keep their original behavior. The empty Saved copy has been updated in all three interface languages.

A separate heart button beside the messager count lets signed-in users like or unlike a real listing. One account contributes at most one like per listing. Counts update optimistically and settle to the database total; failures roll back the displayed state and offer feedback. Repeated clicks are blocked while a mutation is pending. Anonymous users can see the total and receive a login prompt when they press the heart. Liking never saves a bookmark, and saving never creates a like. Existing saved records are not converted to likes.

`listing_likes` has a composite primary key, cascading listing/user foreign keys, and RLS restricting reads to the signed-in user's own likes on visible listings. Authenticated users cannot write the table directly. The idempotent `set_listing_like` RPC derives the actor from `auth.uid()`, locks the listing while changing the desired state, and returns the authoritative total. Anonymous writes and changes to removed listings are denied. The public engagement RPC adds only a count, never liker identities.

`src/features/likes` owns the shared client state, heart control and authenticated server action. The provider reads personal state in paginated batches per session, with focus/auth reconciliation, identity-change invalidation and per-listing pending guards. It makes no per-card reads. All card contexts share local mutations and reuse the existing batched public engagement query. Other visitors see updated totals when their listing data refreshes, including the existing client cache delay; this is not a Realtime subscription.

Validation: lint, TypeScript, production build and 60 Node tests; disposable SQL suites cover privacy, idempotency, unlike, bookmark independence, visible statuses, removal and cascade cleanup, plus prior engagement regression. Isolated browser QA covers anonymous login prompts, persisted likes after reload, save/like independence, unlike, failure rollback, rapid duplicate clicks and mobile/desktop layouts. A hosted smoke test is still needed after applying migration 014. No dependencies or Next.js configuration changes are required.
